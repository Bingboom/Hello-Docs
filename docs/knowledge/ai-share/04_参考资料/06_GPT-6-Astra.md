## 它的专长是什么？

当前 Codex 模型说明把 GPT-6 Astra 定位为面向复杂、高要求任务的高能力模型；随附参考将重点概括为质量优先、推理与较难的编程工作。可以优先考虑让它处理“要求不止一条，而且必须互相配合”的任务。

在这次分享的场景里，可以这样理解：

| 任务特点 | 可以交给它什么 | 自己要看什么 |
| --- | --- | --- |
| 多个要求要同时成立 | 把故事、外观、动作和交互拆成可以实现的部分 | 是否漏要求，结果是否符合原意 |
| 代码之间有依赖 | 协调脚踩踏板、车轮旋转、背景移动和暂停状态 | 动作是否连贯，暂停和恢复是否正常 |
| 需要一边运行一边修正 | 查看现有代码，定位问题，修改后再验证 | 问题是否真的消失，有没有影响别的功能 |
| 要交付可继续修改的作品 | 整理 HTML、样式和脚本，说明在哪里改文字、颜色与速度 | 文件能否独立打开，修改入口是否清楚 |

这些是适合尝试的任务类型，不是每次都能成功的保证。简单改一句话或替换一个链接，也不一定需要选择最复杂的模型。

## 这只鹈鹕体现了哪些工作？

从这份文件本身可以看到三层配合：

- **画出来：** 用 SVG 描述鹈鹕、车架、车轮和海边背景，放大后仍保持清晰。
- **动起来：** JavaScript 根据时间更新车轮、踏板、腿部和背景的位置。腿部不是随意摆动，而是根据脚踏板的位置计算关节位置。
- **用起来：** 暂停、继续、调速和车铃都对应具体行为；文件还考虑了系统的减少动态效果偏好。

有审美的画面只是其中一部分。更值得观察的是：这些要求能否在同一份程序里协调工作，修改一处后其他部分是否仍然正常。

这是一件具体作品的展示，不是官方基准测试，也不能仅凭它判断模型总体排名。代码动画也不等同于模型直接生成视频。

## 同一句提示词，也能用来比较不同模型

本次作品使用的提示词是：

> 生成鹈鹕骑车的 HTML

把同一句话交给不同模型，可以观察它们怎样把一个简短要求变成实际作品。先保存每个模型的首次结果，再分别打开，而不是只看它对自己作品的描述。

| 比较什么 | 打开作品后看什么 |
| --- | --- |
| 是否理解要求 | 主体能否认出是鹈鹕，鸟与自行车的位置是否合理 |
| 视觉与动作表现 | 构图是否清楚；如果做了动画，车轮、踏板和腿部是否连贯 |
| 代码可用性 | HTML 能否在相同浏览器直接打开，是否有报错或缺少资源 |
| 修改能力 | 追加同一项改动后，是否按要求改变，同时保留其他功能 |

尽量固定应用、可用工具、对话上下文和生成机会，并记录模型名称与设置。如果一个模型可以运行浏览器排错，另一个只能输出文字，比较到的就是“模型加工具”的整体效果，不能只归因于模型。

短提示词没有明确要求动画、暂停、调速和车铃。可以观察模型有没有主动加入这些设计，但不能把未要求的功能当成硬性合格线。如果要专门测试动画，再给所有模型统一追加“让脚踩踏板、车轮转动”，作为另一轮测试。

一次生成有偶然性，可以多试几次并保留所有结果，不只挑最好的一张。本文尚未做多模型实测，因此没有给出排名或胜负结论。

## 做出来之后，再改一点

第一次做好后，不必推倒重来。可以继续说：“只把围巾改成蓝色，动作不变”，或者“把速度降一点，保留手动调速”。每次改一处，更容易看出模型是否理解并保留了原有要求。

连接回小林的海报工具，也是同样的做法：说清楚数据、样式、布局和更新规则之间的关系，让 Agent 实现，再用真实结果逐项核对。

海报还可以成为下一步的起点：同一份资料生成多种活动物料，做成能筛选、下载的产品展示页，再收集反馈、提出下一版文案建议。这些尚未完成的延伸场景放在 [主稿第四节：接下来还能往哪儿走](../index.html#s3)。它们将更多关联、例外处理和跨工具协作放到一起，适合用来继续检验模型，而不是直接当成已经验证的能力成绩。

## 使用时记住两个边界

**模型能力与工具权限是两回事。** 模型负责理解、推理和生成代码；能否读取文件、运行浏览器、上传钉钉，还取决于当前应用提供的工具与授权。模型不会因为更强，就自动拥有账号权限。

**作品效果与验收结论是两回事。** 看起来流畅，不代表所有尺寸、浏览器和操作都测过。交付前仍要打开、点击、修改、复查，不能把“已写代码”当成“已经做好”。
